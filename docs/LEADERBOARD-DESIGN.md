# 打榜机制设计稿 · LEADERBOARD DESIGN

> 状态：**设计稿（只写文档，不实现）** —— v2.0「稳定与手感」Phase 2 交付物
> 适用范围：AI PRODUCT RPG + NOVA 概念试炼塔（纯前端、零依赖、localStorage、GitHub Pages）
> 本文档给决策留白：所有方案均不预设结论，等维护者拍板后再立项。

---

## 0. 一句话背景

两款游戏目前都是纯本地进度（`aiProductRpg.v1` / `conceptTower.v1`），玩家之间没有任何「一起在学」的感知。
打榜机制的目的是制造**正向学习压力与陪伴感**，而不是制造排名焦虑。

---

## 1. 设计原则（先定调，再谈技术）

| # | 原则 | 含义 |
|---|------|------|
| P1 | **不展示名次** | 永远不出现「你超过了 87% 的玩家」或排行榜列表页。名次是零和叙事，与陪伴式学习冲突 |
| P2 | **正向叙事** | 文案只用「你的贡献点亮了第 N 层塔」「今天有 X 位同学和你一起净化了暗影」这类集体+个人增量的表达 |
| P3 | **个人增量曲线** | 主视觉是玩家自己的成长曲线（首答正确率、净化数、连续学习天数），他人数据只做背景氛围 |
| P4 | **里程碑徽章** | 社交层的最小单元是徽章/成就（本地已有 ACH 系统 18 枚，可直接复用为「可晒」资产），不是分数 |
| P5 | **防刷优先** | 任何贡献值体系上线前必须先有每日上限与异常剔除，否则榜单数据会迅速失真、反噬激励 |

## 2. 贡献值体系草案

### 2.1 折算公式（草案，系数待定）

```
每日贡献值 = 答对题数 × A
           + 净化暗影数 × B
           + 连续学习天数加成 × C（如 streak≥3 时当日 ×1.2，封顶 ×1.5）
           + 成就解锁数 × D（仅首次解锁计入）
           ，上限 = 每日上限 cap（如 120）
```

| 变量 | 建议初值 | 说明 |
|------|---------|------|
| A（答对） | 1 | 只计首答正确的题；同一天重复答对同一题只计 1 次 |
| B（净化） | 5 | 暗影净化是「错题真正掌握」的最强信号，权重最高 |
| C（连学加成） | ×1.2~1.5 | 断签即清零；鼓励连续而非爆肝 |
| D（成就） | 10 | 成就本身去重，天然防刷 |
| cap（日上限） | 120 | 约 = 认真玩 1 小时的自然产出；超出部分只进个人曲线、不进共享层 |

### 2.2 防刷设计（必须先于任何同步方案落地）

- **每日上限**：见 cap，超过后 UI 明示「今日贡献已满，继续学习只记入个人曲线」。
- **重复去重**：题目 id 级别的当日去重表（本地可存 `contrib.day = {date, seenIds}`）。
- **时长合理性**：单题作答间隔 < 1.5s 视为脚本行为，不计贡献（本地可判）。
- **异常剔除（服务端方案才有）**：单账号日贡献分布长期贴 cap 且作答间隔方差趋零 → 打标不入聚合。
- **不奖励重置**：重置存档/清 localStorage 不清贡献历史（贡献按天聚合后不可回退）。

## 3. 三种同步方案对比

| 维度 | A. 零后端：挑战码互验 | B. GitHub Issues 免费后端 | C. 轻后端（Cloudflare Workers / 腾讯云开发） |
|------|----------------------|--------------------------|----------------------------------------------|
| 原理 | 复用现有存档码，再导出一张「贡献码」（含贡献值+成就摘要+HMAC 签名），线下（群/Issue/朋友圈）互相比对、互相点亮 | 玩家一键「上报」，前端以固定格式往指定 repo 的 Issue/Comment 写数据；页面定期拉取聚合（GitHub API 匿名限额 60 req/h） | 一个 ~100 行的 Worker：`POST /contrib` 写 KV/D1，`GET /summary` 出聚合数；未来云端化可直接复用该接口 |
| 零依赖纯前端 | ✅ 完全保持 | ⚠️ 依赖 GitHub API 与 PAT（个人令牌） | ❌ 引入服务端（但仍可做到游戏本体零依赖，仅打榜模块联网） |
| 成本 | 0 | 0（公共 repo API 限额内） | Workers 免费额度足够；云开发有免费层 |
| 隐私 | 最好：数据不出本地，出示多少自愿 | 一般：昵称/贡献码公开可见 | 好：可匿名 deviceKey，不强制注册 |
| 防刷 | 弱（靠签名防篡改，无法防重放多设备） | 中（可 Issue 去重，但匿名上报可刷） | 强（服务端 cap 与异常剔除） |
| 「N 层塔」集体叙事 | 差（只能小圈子互看） | 中（可聚合全 repo） | 好（实时聚合，可做「今日全服点亮层数」） |
| 维护负担 | 无 | 低-中（要管 Issue 楼层、防灌水） | 中（上线后要管配额/告警/滥用） |
| 未来云端化复用 | ❌ | ❌ | ✅ 同一接口直接复用 |
| 失效模式 | 无 | PAT 泄露 / API 限额 / Issue 被灌水 | 服务被刷导致 KV 写爆；域名被墙 |

### 3.1 推荐（供讨论，非结论）

- **短期（1-2 周内可做）**：方案 A。在「系统」弹窗里加「📤 导出贡献码」，码内含 `贡献值/成就摘要/签名`；README 开一节「晒码区」。零风险、零维护，先验证玩家是否有晒的需求。
- **中期**：若 A 的参与度可观测（Issue 里晒码的多），上方案 B，把晒码区搬进一个专用 Issue，前端聚合展示「本周全仓点亮层数」。
- **长期 / 云端化**：方案 C。Cloudflare Workers + D1 一张表即可；接口设计时预留 `POST /contrib`（防重放 nonce）与 `GET /summary`，与 Web 同源复用。

### 3.2 风险与开放问题

1. 贡献值若可见，是否仍会诱发内卷？（P1 的「无名次」能缓解到什么程度，需要灰度观察）
2. 方案 B 的 PAT 放在前端分发存在滥用风险——是否改为「扫码跳转 GitHub 授权」？
3. 签名密钥放在纯前端等于公开，方案 A 的 HMAC 只防误改不防恶意伪造——接受度？
4. 每日挑战（已上线的种子塔）是否计入贡献值 ×2？建议：计入但同样吃 cap。
5. 断签保护（补签卡？冻结一天？）是否需要，避免 streak 设计变成焦虑源。

## 4. UI 挂点建议（实现时参考）

- RPG「系统」弹窗与塔「战报」弹窗顶部已有成就墙入口，打榜入口与其并列，不新增顶栏按钮。
- 集体叙事位：塔标题卡「🎴 每日挑战」区块下方加一行「今日全服共点亮 N 层」（方案 B/C 才有数据）。
- 个人曲线位：成就墙顶部，用现有 `{cur,max}` 进度体系画 7 日迷你柱状图。
