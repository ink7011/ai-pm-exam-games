# 迭代工作流 · Builder / Reviewer 分离
# WORKFLOW · Separate the Builder from the Reviewer

> **核心理念**：同一个大脑既写代码又审代码，会有「裁判兼运动员」的认知盲区——
> Builder 倾向「积极生成，让它能跑」；Reviewer 倾向「批判审查，专找它跑不动的那一刻」。
> 两个角色必须分离，规则各自加载，互不污染上下文。
>
> *The same brain that wrote the code will confirm its own bugs. Builder generates; Reviewer hunts. Separate the roles, load different rules, keep the contexts isolated.*

---

## 一 · 五步迭代环 / The Loop

```
grill-with-docs ──▶ to-spec ──▶ to-tickets ──▶ implement ──▶ code-review ──┐
      ▲                                                                │
      └────────────────── 下一轮迭代 ◀──────────────────────────────────┘
```

| 步骤 | 角色 | 产出 | 通过条件 |
|---|---|---|---|
| **1. grill-with-docs** 需求追问 | Reviewer 主导 | 3-5 个边界问题 + 优先级排序 | 维护者逐题拍板 |
| **2. to-spec** 规格化 | Builder | Spec 文档：目标/非目标/验收标准/风险 | 维护者确认「没有要改的」 |
| **3. to-tickets** 拆票 | Builder | 带验收标准的执行票 | 每票可独立验证 |
| **4. implement** 实现 | **Builder Agent**（后台长程） | 代码 + 自测 | `node tools/smoke.js` 全绿 |
| **5. code-review** 审查 | **Reviewer Agent**（独立上下文） | 修改建议清单（必修/登记分级） | 维护者确认后才修 |

**长程任务的协作结构**：implement 可挂后台代理执行，但代理**禁止 git、禁止碰文档正典**；完成通知后必须过**人工验收关卡**（复跑冒烟 → 浏览器实测 → 文档同步 → 提交推送）。

## 二 · Builder 规则 / Builder Rules

1. **零依赖纯 vanilla**：无框架、无构建、无上报；localStorage 即数据库。
2. **防御式取值**：读档一律 `|| 默认值`；load/save 全部 try/catch。
3. **写文件先数数**：批量替换类脚本必须逐条 `assert count==1`，失败就不写盘（防半成品文件）。
4. **缓存纪律**：改任何 JS 必升引用处 `?v=`；动 `sw.js` 缓存清单必递增 `CACHE` 版本号。
5. **交付门槛**：`node tools/smoke.js` 全绿才算完成——语法、题库完整性、边界用例、关键时序全在里面。
6. **正典先行**：世界观/动画文案改动，先改 `docs/WORLDVIEW.md` 再同步代码常量。

## 三 · Reviewer 规则 / Reviewer Rules

1. **立场**：假设代码有罪。找的是「玩家会遇到的那一刻」，不是「代码好看与否」。
2. **证据**：每条发现必须给 `file:line` + 触发路径（怎么点/怎么按/怎么刷新才会炸）。
3. **分级**：🔴 必修（损数据/卡死）→ 🟠 高优（可复现体验事故）→ 🟡 登记（可接受+备忘）→ ⚪ 备注。
4. **也要验证「负空间」**：挑过没挑出来的要明说（审计通过项），避免只报忧不报全貌。
5. **实机 Playtest 是审查的一部分**：键盘、弹窗、刷新恢复、断网，都是键盘侠玩家的真实路径。

### Reviewer 第二顶帽子 · 灵魂审查 / The Soul Review（V0.6 起）

系统审查问"它会不会坏"；**灵魂审查问"它好不好耍"**。两顶帽子都要戴，结论分开给。

**第一性原则：Play first. Learn along the way. 耍中找学，学中来耍，以耍为主。**
玩家必须先感到"好玩，我想看接下来会发生什么"，然后才意识到"我学到东西了"。顺序不可颠倒。

灵魂审查的首要问题永远是：**这会让玩家想继续耍吗？**（不是"有没有教育价值"，也不是"留存是否提升"。）

**红旗清单（"假游戏"检测）**——命中即显式标记 `🃏 穿着游戏外衣的题库`：
- 有唯一明显正确答案的"决策"；每次选择后果空洞；先讲解后发生（应先发生后反思）
- 不影响游戏本身的徽章/XP；铺在静态内容上的装饰性 gamification
- 为"讲一个知识点"而存在的场景；结果完全可预测

**保护清单**：好奇心（"选这个会怎样？"）· 真后果（决策改变世界）· 意外（偶发的惊奇）· 取舍（很少有两全）· 涌现（前决策长出新问题）· 主体性（"这是我的选择造成的"）· 个性（幽默/张力/戏剧/可传播的名场面）· 重玩价值（"换条路会怎样？"）

**反功利红线**：不向 职业焦虑/简历价值/效率优化 全面投降。允许玩家试错、作死、走奇怪的路、制造故事——最有记忆点的玩法常来自灾难与意外。宁可"更有趣但略无用"，不可"更有用但更无趣"（在职业世界仍真实的前提下）。

**两个口头测试**：
- 传播测试：玩家会跟朋友讲刚才发生的事吗？（"我开除了最强工程师然后产品崩了"=好；"我做完了第 8 题得了 85 分"=坏）
- 再来一局测试：这个瞬间之后，玩家想看下一幕吗？（而不是"课程完成"感）

**评分维度与优先级**：🎮 可玩性 > 🧠 主体性 > 🔥 情绪投入 > 🌍 世界响应 > 🌀 涌现 > 🔁 重玩性 > 🎓 隐形学习。
输出格式：Verdict（APPROVE / APPROVE WITH CONCERNS / REWORK）+ 四项分数（可玩/主体性/情绪/隐形学习，各 X/10）+ What Works / Too Educational / Too Utilitarian / Biggest Risk / Recommended Changes。

**终极裁判规则：当"更有教育价值"与"更好耍"冲突时，选好耍——只要职业世界仍然真实。**
我们不是在做课程、题库或测评。我们在做一个玩家想进入的世界。学习很重要，但要让玩家在耍中发现它。

### Reviewer 检查清单（本项目实战版）

- [ ] 键盘路由：弹窗开着会不会「隐形答题」？过场动画期间 Enter 会不会双触发？
- [ ] 状态时序：动画中刷新会不会状态回退？双击/连按会不会重复结算？
- [ ] 落盘安全：定时器闭包 vs 直写 localStorage 是否同源（药剂被冲掉的教训）？
- [ ] 死代码与孤儿：计划外产物（未被引用的文件）是否混进提交？缓存清单里有没有 404 定时炸弹？
- [ ] 成就/统计可达性：引用的字段是否真的有人维护（防「永远点不亮的成就」）？
- [ ] SW/缓存：cache-first 的资源部署后何时可见？`addAll` 遇 404 会整体失败？
- [ ] 防刷口径：每日成绩是否绕过生涯积分？测试钩子是否提权？

## 四 · 实战注脚 / War Stories（本仓库真实发生）

- **sw.js 404 炸弹**：实现代理删除了一个孤儿文件，但 Service Worker 缓存清单里还留着它——`cache.addAll` 遇 404 会整体失败，SW 永远装不上。人工验收关卡拦下。
- **双份世界观**：同一代理产出过一套与正典冲突的 STORY.md。教训：**文档正典只能由维护者侧改动**，此后写入 Builder 规则第 6 条。
- **键盘隐形答题**：塔加了弹窗门控、RPG 漏了同款（两个文件、两次实现、一个忘抄）。教训：同构逻辑必须 Reviewer 逐文件对照。
- **测试环境假象**：「按钮点不动」排查半天，实为测试浏览器标签冻结。教训：先做活页对照实验（点已知好按钮），再怀疑代码。
